[challenger stderr] ## Drafting Guidance
[challenger stderr] 
[challenger stderr] - Before writing a full draft, decompose the natural-language requirements into system boundary, environment inputs, system outputs, assumptions, guarantees, initial conditions, safety/update rules, liveness/justice requirements, and response/pattern requirements.
[challenger stderr] - Add requirement groups incrementally in reasoning. After each group, check for ownership mistakes, hidden assumptions, contradictory initial conditions, over-strong guarantees, duplicate constraints, and unused variables.
[challenger stderr] - Start with one named `spec`.
[challenger stderr] - Declare environment variables with `env` and system variables with `sys`.
[challenger stderr] - Encode assumptions with `asm` and guarantees with `gar`.
[challenger stderr] - Add environment assumptions only when the description states or strongly implies an environment constraint.
[challenger stderr] - Prefer a minimal complete model over speculative features.
[challenger stderr] - Prefer the simplest Spectra construct that directly expresses the requirement.
[challenger stderr] - Use advanced constructs such as `counter`, `monitor`, `pattern`, `regexp`, quantifiers, aggregates, and triggers only when the natural-language description clearly calls for them or they materially simplify the specification.
[challenger stderr] - If the description leaves key semantics unstated, make the smallest explicit assumption and report it.

[challenger stderr] ## Unrealizability-Repair Loop
[challenger stderr] 
[challenger stderr] 1. Run the CLI and confirm the specification is syntactically valid but unrealizable.
[challenger stderr] 2. Request a counter-strategy diagnostic.
[challenger stderr] 3. Request an unrealizable-core diagnostic.
[challenger stderr] 4. Identify a likely conflict between assumptions, guarantees, initial conditions, safety, liveness, or update rules. Use the core to focus attention on the implicated guarantee lines, and use the counter-strategy to understand a concrete environment-winning behavior.
[challenger stderr] 5. Compare any candidate repair against the natural-language description.
[challenger stderr] 6. Apply the candidate only when it is consistent with the description.
[challenger stderr] 7. Re-run the normal CLI check.
[challenger stderr] 8. Stop after 3 unrealizability-repair attempts or when all plausible repairs would contradict the description.
[challenger stderr] 
[challenger stderr] Common repair patterns:
[challenger stderr] 
[challenger stderr] - Add a missing environment assumption only when the description says the environment is constrained.
[challenger stderr] - Repair an initial condition that conflicts with an immediate response requirement.
[challenger stderr] - Replace an accidental always-immediate response with a next-step response if the description allows delayed reaction.
[challenger stderr] - Remove an over-specific liveness condition only when the description does not require that recurrence.
[challenger stderr] 
[challenger stderr] Common invalid repairs:
[challenger stderr] 
[challenger stderr] - Deleting a stated guarantee solely to make synthesis succeed.
[challenger stderr] - Adding an assumption that forbids inputs the description explicitly permits.
[challenger stderr] - Weakening "must always" into "may sometimes" without textual support.
[challenger stderr] - Ignoring a named input/output or changing control ownership.
[challenger stderr] 
[challenger stderr] ## Well-Separation Loop
[challenger stderr] 
[challenger stderr] 1. Run the well-separation check only after the normal check reports `Result: Specification is realizable`.
[challenger stderr] 2. If the result is non-well-separated, inspect environment assumptions first, especially assumptions that mention system variables or depend on system-controlled behavior.
[challenger stderr] 3. Compare any candidate repair against the natural-language description.
[challenger stderr] 4. Apply a repair only when it is consistent with the description.
[challenger stderr] 5. Re-run the normal CLI check and then the well-separation check.
[challenger stderr] 6. Stop after 3 well-separation-repair attempts or when all plausible repairs would contradict the description.

[incumbent stderr] ## Drafting Guidance
[incumbent stderr] 
[incumbent stderr] - Before writing a full draft, decompose the natural-language requirements into system boundary, environment inputs, system outputs, assumptions, guarantees, initial conditions, safety/update rules, liveness/justice requirements, and response/pattern requirements.
[incumbent stderr] - Add requirement groups incrementally in reasoning. After each group, check for ownership mistakes, hidden assumptions, contradictory initial conditions, over-strong guarantees, duplicate constraints, and unused variables.
[incumbent stderr] - Start with one named `spec`.
[incumbent stderr] - Declare environment variables with `env` and system variables with `sys`.
[incumbent stderr] - Encode assumptions with `asm` and guarantees with `gar`.
[incumbent stderr] - Add environment assumptions only when the description states or strongly implies an environment constraint.
[incumbent stderr] - Prefer a minimal complete model over speculative features.
[incumbent stderr] - Prefer the simplest Spectra construct that directly expresses the requirement.
[incumbent stderr] - Use advanced constructs such as `counter`, `monitor`, `pattern`, `regexp`, quantifiers, aggregates, and triggers only when the natural-language description clearly calls for them or they materially simplify the specification.
[incumbent stderr] - If the description leaves key semantics unstated, make the smallest explicit assumption and report it.

[incumbent stderr] ## Syntax-Repair Loop
[incumbent stderr] 
[incumbent stderr] 1. Save the draft as a `.spectra` file.
[incumbent stderr] 2. Run the CLI.
[incumbent stderr] 3. If parsing fails, extract the parser message, for example `missing ';' at 'gar'`.
[incumbent stderr] 4. Repair the file with the smallest syntax-preserving edit.
[incumbent stderr] 5. Repeat until the file is syntactically valid or the attempt budget is exhausted.

[incumbent stderr] ## Unrealizability-Repair Loop
[incumbent stderr] 
[incumbent stderr] 1. Run the CLI and confirm the specification is syntactically valid but unrealizable.
[incumbent stderr] 2. Request a counter-strategy diagnostic.
[incumbent stderr] 3. Request an unrealizable-core diagnostic.
[incumbent stderr] 4. Identify a likely conflict between assumptions, guarantees, initial conditions, safety, liveness, or update rules. Use the core to focus attention on the implicated guarantee lines, and use the counter-strategy to understand a concrete environment-winning behavior.
[incumbent stderr] 5. Compare any candidate repair against the natural-language description.
[incumbent stderr] 6. Apply the candidate only when it is consistent with the description.
[incumbent stderr] 7. Re-run the normal CLI check.
[incumbent stderr] 8. Stop after 3 unrealizability-repair attempts or when all plausible repairs would contradict the description.
